# ADR 0002：CI/CD 与仓库治理

- 状态：已采纳
- 日期：2026-09-27
- 范围：`.github/`、`release-please-config.json`、`.gitleaks.toml`、`apps/web/Dockerfile`

## 背景

仓库已公开在 GitHub（`Renkos1/QiC`）。需要一套流水线保证：每个 PR 经过与本地 `pnpm check` 相同的检查；生产构建特有的问题在合并前后能被发现；发布产物可追溯（SBOM、签名、digest）；部署与回滚可重复执行。镜像仓库和服务器目前都没有确定，流水线必须在它们缺席时照常工作。

## 决策

| 决策 | 结论 | 原因 |
|---|---|---|
| 工作流划分 | `ci`、`e2e`、`security`、`release`、`deploy` 五个工作流；共用步骤放在 `.github/actions/setup` 与 `.github/actions/build-images` | 每个工作流职责单一，失败时一眼看出是哪一类问题 |
| 工具版本 | CI 同样用 mise 按 `.mise.toml` 安装 Node、pnpm、oasdiff | 本地与 CI 版本只在一处定义 |
| 缓存 | pnpm store 按 lockfile 缓存；turbo 本地缓存按 job 缓存；镜像层用 BuildKit 的 GitHub Actions 缓存 | 不引入 turbo 远程缓存服务 |
| 受影响范围 | PR 上 typecheck/test 用 `turbo --affected`；main 全量运行（大多命中缓存） | PR 反馈快，main 仍完整验证 |
| 集成测试 | 直接运行 Testcontainers（GitHub runner 自带 Docker），**不使用** service containers | 与本地运行方式相同，无需维护第二套数据库配置（计划中的 service 方式未采用） |
| e2e | PR 跑 `@smoke`（开发服务器）；main 用生产镜像经 `infra/compose/deploy.sh` 部署后跑全量；PR 加 `e2e:production` 标签也可跑 | 生产构建的预取缓存、水合时序问题只在生产构建出现；同时演练了真实部署脚本 |
| 生成文件 | CI 运行 `pnpm gen` 后要求工作区无差异 | 保证契约修改后生成文件已提交 |
| 安全扫描 | CodeQL、gitleaks、`pnpm audit --audit-level high`；每周重新构建镜像并用 Trivy 扫描（HIGH/CRITICAL 且有修复版本时失败） | 新公布的漏洞在代码不变时也能发现 |
| 密钥扫描白名单 | `.gitleaks.toml` 只放行具体的测试固定值，不按文件放行 | 测试文件中出现真实密钥仍会被拦截 |
| 发布 | release-please（单一版本，根 `package.json`，tag 为 `vX.Y.Z`）；发布时构建 → Trivy → SBOM（SPDX）→ 附加到 GitHub Release | 版本与 CHANGELOG 由提交信息自动生成 |
| 发布开关 | `IMAGE_REGISTRY` 设置后才推送并用 cosign 无密钥签名、附加 SBOM 证明；`SENTRY_AUTH_TOKEN` 设置后才上传 source map | 没有外部服务时流水线照常完成 |
| 镜像构建演练 | 修改 Dockerfile、`.dockerignore` 或构建 action 的 PR 会跑一次不发布的 release | 镜像问题在合并前暴露 |
| web 构建参数 | `NEXT_PUBLIC_*` 与 `SENTRY_ORG/PROJECT` 作为构建参数传入；`SENTRY_AUTH_TOKEN` 作为 BuildKit secret，不进入镜像层 | 浏览器变量必须在构建时确定；token 不能留在镜像里 |
| 部署 | `deploy.yml` 读取 Release 附带的 `images.env`（digest），经 SSH 复制 compose 文件并执行 `deploy.sh`；`production` environment 审批；主机指纹通过 `DEPLOY_KNOWN_HOSTS` 固定 | 始终按 digest 部署；回滚 = 部署旧 tag，或服务器上的 `rollback.sh` |
| 部署触发 | 由 `release.yml` 以可复用工作流方式调用（`AUTO_DEPLOY=true`），或手动触发；**不**监听 `release: published` | GITHUB_TOKEN 创建的 Release 不会触发其他工作流 |
| Action 固定 | 全部固定到 commit SHA，后缀写版本注释；Renovate 负责更新 | 防止 tag 被改写带来的供应链风险 |
| 依赖更新 | Renovate 每周一分组；minor/patch 在必需检查通过后自动合并；Node、pnpm 各自成组、不自动合并 | 降低更新噪音；运行时版本升级需要人确认 |

## 影响

- 分支保护、合并方式、Renovate 安装、`production` environment 等无法写进代码，需要在 GitHub 上人工配置一次（清单见 README “仓库设置”）。
- release-please 用 `GITHUB_TOKEN` 开的发布 PR 不会触发 CI；在分支保护要求必需检查的情况下，需要配置 `RELEASE_PLEASE_TOKEN`。
- main 上的生产 e2e 每次都要构建三个镜像，耗时明显长于 PR 冒烟；由构建缓存缓解。
- 部署后的检查只有 `smoke.sh`（首页、API、内部端点不对外）；不在生产环境跑 e2e，以免产生测试账号。
